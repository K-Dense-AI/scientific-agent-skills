# Setup, Versions, and Credentials

## Verified Version Baseline

Checked against PyPI JSON and executed against a real install on **2026-09-30**:

| Distribution | Verified version | Purpose | Notes |
|---|---:|---|---|
| `pytket` | 2.18.4 | Core circuits, compilation, backends abstraction | Python >=3.10 (classifiers 3.10–3.14), 64-bit; Windows wheel `cp312-abi3` |
| `pytket-qiskit` | 0.78.0 | Qiskit conversion + **all Aer/IBM backends** | Use the `[aer]` extra for simulation; needs `pytket>=2.11`, `qiskit>=2.3`, Python 3.11–3.14 |
| `qiskit` | 2.5.2 | Pulled in by `pytket-qiskit` | |
| `qiskit-aer` | 0.17.2 | Pulled in by the `[aer]` extra | Upstream README: "no longer actively maintained" |
| `qiskit-ibm-runtime` | 0.50.0 | IBM hardware via `IBMQBackend` | |
| `pytket-quantinuum` | 0.59.3 | Quantinuum compile target + local emulation | **Since 0.56.0 it refuses hardware submission — use `qnexus`** |
| `qermit` | 0.9.3 | ZNE / CDR / frame randomisation error mitigation | **Conflicts with the two rows above** — pin `pytket-qiskit<0.78` and `pytket-quantinuum[pecos]<0.59`; see [The `qermit` conflict](#the-qermit-conflict-verified-2026-10-01) |
| `numpy` / `scipy` / `sympy` | 2.5.3 / 1.18.1 / 1.14.0 | Versions actually resolved alongside the pins above | pytket floors: `numpy>=1.26.4`, `scipy>=1.13.1`, `sympy>=1.12.1` |

Re-verify with the PyPI JSON endpoints (`https://pypi.org/pypi/<dist>/json`) and
`importlib.metadata.version(...)` in a fresh venv; see [sources.md](sources.md).

## Create an Environment

macOS / Linux:

```bash
python3 -m venv .venv-tket
source .venv-tket/bin/activate
python -m pip install --upgrade pip
```

Windows (PowerShell):

```powershell
python -m venv .venv-tket
.venv-tket\Scripts\Activate.ps1
python -m pip install --upgrade pip
```

Install, smallest first:

```bash
# Core only: circuits, compilation, QASM 2, ZX, no simulator
python -m pip install pytket

# Local simulation (AerBackend, AerStateBackend, AerUnitaryBackend, IBMQEmulatorBackend)
python -m pip install "pytket-qiskit[aer]"

# Optional extras
python -m pip install "pytket[zx]"              # quimb/numba/autoray for ZX tensor evaluation
python -m pip install "pytket-quantinuum[pecos]" # H2-1LE local emulator (pytket-pecos, quantum-pecos, pytket-phir)
python -m pip install qermit                     # zero-noise extrapolation, CDR, frame randomisation
```

Resolve everything together in one fresh environment. Do not install extensions one at a time
into a working environment (see [Extension version coupling](#extension-version-coupling)).

### The `pytket-aer` trap

**There is no `pytket-aer` package** — `pip install pytket-aer` fails with
`No matching distribution found`. The Aer backends ship inside `pytket-qiskit`:

```python
from pytket.extensions.qiskit import AerBackend  # NOT pytket.extensions.aer, NOT pytket_aer
```

Without the `[aer]` extra this import raises `ImportError` (qiskit-aer missing). Fix:
`python -m pip install "pytket-qiskit[aer]"`.

## Platform Notes

- Python >=3.10, 64-bit; wheels for Linux, macOS 13+, Windows. LTSC Windows is unsupported.
- **macOS + conda**: known issue ([tket#926](https://github.com/quantinuum/tket/issues/926)) caps
  installs at pytket 1.11.0. The only known remedy is an official Python distribution
  (python.org / Homebrew), not the conda interpreter.
- **M1/arm64 macOS**: if `scipy` fails to build, `brew install openblas`, then
  `OPENBLAS="$(brew --prefix openblas)" pip install scipy`, then `pip install pytket`.
- `pytket.__version__` is generated by `setuptools_scm` at wheel-build time — it exists only in an
  **installed** pytket, not in a source checkout. Do not grep a clone for it.
- pytket core extras: only `[zx]` exists. There is **no `[visualization]` extra**; circuit drawing
  needs the `graphviz` system binary for `pytket.utils.Graph` output formats beyond the defaults,
  plus a separate `pytket-offline-display` package for offline rendering.

Smoke test (no network, no credentials):

```python
from pytket.circuit import Circuit
from pytket.extensions.qiskit import AerBackend

c = Circuit(2).H(0).CX(0, 1).measure_all()
backend = AerBackend()
counts = backend.run_circuit(c, n_shots=100, seed=7).get_counts()
print(counts)   # keys are bit-tuples, ILO-BE: {(0, 0): ~50, (1, 1): ~50}
```

## Extension Version Coupling

Every extension pins a compatible `pytket` range, so **installing an extension can silently move
pytket** (pytket-qiskit changelog history: minimum pytket 2.8.0 → 2.9.3 → 2.10.3 → 2.11; qiskit
pins have moved too, e.g. `~=1.2.4` → `<2.1` → `>=2.3`). A stale pin is also why `pytket-qsharp`
(`pytket ~=1.26`) cannot be installed alongside pytket 2.x at all.

Portable checks after any install:

```bash
pip show pytket-qiskit                        # Version: and Requires: lines
python -c "import pytket; print(pytket.__version__)"
python -c "import importlib.metadata as m; print(m.version('pytket-qiskit'))"
python -c "import importlib.metadata as m; print('\n'.join(m.requires('pytket-qiskit')))"
```

If `import pytket` suddenly fails or behaves like an older release after installing an extension,
an incompatible pytket got resolved in. Rebuild the venv and install all pins in one command.

### The `qermit` conflict (verified 2026-10-01)

`qermit` pins the **Qiskit and Quantinuum extensions**, not just pytket. From the wheel metadata of
each release:

| `qermit` | `pytket-qiskit` pin | `pytket-quantinuum[pecos]` pin |
|---:|---|---|
| 0.8.5 | `>=0.73,<0.74` | `>=0.41,<0.55` |
| 0.8.6 – 0.9.2 | `>=0.73,<0.78` | `>=0.41,<0.58` |
| 0.9.3 (latest) | `>=0.73,<0.78` | `>=0.41,<0.59` |

So **no released `qermit` is compatible with `pytket-qiskit` 0.78.0**, and none is compatible with
`pytket-quantinuum` 0.59.x. Resolving `qermit` together with the current extension releases does
not fail — pip silently backtracks all the way to **`qermit` 0.7.1**, an old release whose pins are
loose enough to coexist. That is a much older error-mitigation API than the one the docs describe.

Consequences, and what to do:

- Do **not** install `qermit` into the same environment as the current `pytket-qiskit` /
  `pytket-quantinuum`. Give ZNE/CDR/PEC work its **own venv** and let the resolver pick a consistent
  set, then read the versions it chose before trusting any API from the docs.
- Alternatively pin the extensions down to what `qermit` 0.9.3 accepts
  (`pytket-qiskit<0.78`, `pytket-quantinuum[pecos]<0.59`) and accept an older simulator extension.
- Always confirm what actually landed:
  `python -c "import importlib.metadata as m; print(m.version('qermit'))"`.
- This skill's core, compilation, backend, and interop material does **not** depend on `qermit`.
  Only [noise.md](noise.md) does, and it flags the split explicitly.

## Credentials

### pytket config file (JSON, not TOML)

`pytket.config` manages one JSON file at `$XDG_CONFIG_HOME/pytket/config.json`, else
`~/.config/pytket/config.json`:

```python
from pytket.config import (PytketConfig, PytketExtConfig,
                           get_config_file_path, load_config_file, write_config_file)
```

There is **no `TKETConfig`, no `set_tket_config`, and no TOML** — those names do not exist.
Extensions persist credentials by subclassing `PytketExtConfig` and writing into the
`extensions` dict of that file. Never print, log, or commit it.

### IBM (via pytket-qiskit)

Put the token in the process environment first — never hardcode, print, or commit it:

```bash
# POSIX
export IBM_QUANTUM_API_KEY="set-this-outside-source-control"
```

```powershell
# Windows PowerShell
$env:IBM_QUANTUM_API_KEY = "set-this-outside-source-control"
```

```python
import os
from pytket.extensions.qiskit import set_ibmq_config, IBMQBackend

set_ibmq_config(ibmq_api_token=os.environ["IBM_QUANTUM_API_KEY"],
                instance=os.environ.get("IBM_QUANTUM_INSTANCE"))  # writes the pytket config file
backend = IBMQBackend("ibm_fez")   # name from your IBM Quantum Platform instance, not a tutorial
```

For CI/ephemeral machines, skip `set_ibmq_config` and pass `token=os.environ["IBM_QUANTUM_API_KEY"]`
straight to `IBMQBackend(...)`. If a token leaks, revoke it in IBM Cloud immediately.

### Quantinuum

`QuantinuumConfig` fields are exactly `username, refresh_token, id_token, refresh_token_timeout,
id_token_timeout` — **there is no `api_token` field**. Since pytket-quantinuum 0.56.0 the package
does not submit to hardware; real QPU jobs go through **`qnexus`**:

```python
import os
import qnexus as qnx

qnx.login()   # interactive browser-based login; never paste tokens into source
```

Keep `pytket-quantinuum` for the compile target (`QuantinuumBackend(device_name=...)` — the
parameter is `device_name`, not `machine_name`), `QuantinuumBackendCompilationConfig`, and the
`[pecos]` local emulator (`H2-1LE`). In `qnexus`, cap cost with `max_cost` (HQC); there is no
`backend.cost()` method. All tokens come from environment variables or the provider's own login
flow — never hardcoded, never printed, never committed.

## Debugging and Logging

`pytket.logging` (the names are `set_level` and `level` — **not** `set_log_level`/`get_log_level`,
which do not exist, and there is no getter):

```python
from pytket.logging import level, set_level
set_level(level.debug)    # trace=0, debug, info, warn, err=4 (default), critical, off
# ... re-run the failing pass/conversion; C++-side diagnostics go to stderr ...
set_level(level.err)      # restore; trace is very verbose
```

Raise verbosity when a compilation pass appears to do nothing (no error, circuit unchanged) or a
conversion emits something unexpected — the C++ layer logs the reason it skipped work only at
`debug`/`trace`.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ImportError` on `from pytket.extensions.qiskit import AerBackend` | Installed `pytket-qiskit` without the `[aer]` extra | `pip install "pytket-qiskit[aer]"` |
| `No matching distribution found for pytket-aer` | Package does not exist | Aer backends live in `pytket-qiskit` |
| `ModuleNotFoundError: No module named 'pytket'` after installing an extension | Extension resolved an incompatible pytket out / venv not activated | Rebuild venv, install all pins in one command, check `pip show` output |
| `pip install pytket` yields 1.11.0 on macOS | conda interpreter issue (tket#926) | Use an official Python distribution |
| `pip install pytket` yields an old version elsewhere | Python <3.10 or old pip | Upgrade Python/pip |
| ZX tensor evaluation silently skipped or slow | `quimb`/`numba`/`autoray` absent | `pip install "pytket[zx]"` |
| `pytket.utils.Graph` rendering fails | `graphviz` system binary missing | Install graphviz from your package manager, not just the Python wrapper |
| `AttributeError: module 'pytket' has no attribute '__version__'` | Running from a source checkout | `__version__` exists only in installed wheels |
| Hardware submission refused by pytket-quantinuum | Removed in 0.56.0 | Submit via `qnexus` (`qnx.login()` → `qnx.execute(...)`) |

## Upgrade Policy

1. Pin `pytket` and every extension explicitly; record the resolved numpy/scipy/sympy too.
2. Read the pytket changelog (`pytket/docs/changelog.md` in the Quantinuum/tket repo) and each
   extension's changelog before moving a pin.
3. Re-run the smoke test above plus your compilation snapshots in a fresh venv.
4. Never upgrade in the middle of a paid QPU experiment.
